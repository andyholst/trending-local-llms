# Findings

## The coverage report's derived counts and `--queries` disagreed on a nameless ranked row

- **Evidence:** measured on this branch with a synthetic store of two ranked rows —
  one `id: "named-model"`, one `id: ""` (`scripts/query_coverage.py`): the default
  report printed `2 derived (throughput) + 2 footprint ... added to EACH leg = 51 sent
  in total`, while `--queries` emitted only `named-model tokens per second,
  named-model vram ram context weights offload engine version` (35 curated + 2 per leg
  = 43). Before #1688/PR #1692 the two agreed because `prompt_queries()` returned the
  raw composition unchanged. RED-proved on the base revision:
  `PASSED 90 | FAILED 2`; head `PASSED 92 | FAILED 0`.
- **Why:** `report()` read `UT.all_search_queries()` / `UT.derived_queries()` directly,
  so its counts still included the vacuous empty-id queries `prompt_queries()` drops; a
  reader trusting the report overestimated what each search leg sends.
- **Done when:** the report's derived/footprint/aged counts and its `sent in total` line
  are computed through the same filtered seam as `--queries`, pinned by
  `tests/test_query_coverage.py::test_the_report_counts_only_queries_that_name_a_row`.

## A single HTTP 502 among otherwise-timed-out queries flips a transport outage to a false "quiet search"

- **Evidence:** `scripts/update_trending.py::is_upstream_timeout` recognises
  `timed out` / `timeout` / `522` / `504` / `gateway timeout` but NOT `502` /
  `Bad Gateway`, and `zero_hit_verdict`'s total-outage prong requires
  `timeouts + outage == queries`. Measured on master: run
  [45526182085](https://github.com/andyholst/trending-local-llms/actions/runs/45526182085)
  (push, head `151321c3`) had 34 timeouts + 1 `HTTP Error 502: Bad Gateway`, so
  `timeouts=34 != 35` and the verdict fell through to
  `[error] ... a QUIET SEARCH on a reachable mirror` — `live-smoke` FAILURE, master red,
  every PR's auto-merge blocked. Six minutes later run 45526708331 (PR #1692) had 35/35
  plain timeouts and the SAME code printed `[outage] the lightbrd mirror is UNREACHABLE`
  and stayed green. Identical failure shape, opposite verdicts.
- **Why:** one gateway error breaks the "every query timed out" arithmetic, so a real
  unreachable mirror is misreported as a query-set problem — the exact class rule 6's
  #291/#296 outage handling exists to prevent, and a red `live-smoke` gates every PR.
- **Done when:** a 502/503/504-class gateway error counts as a transport failure (or the
  total-outage prong is re-derived so one unclassified gateway error cannot flip it),
  with a RED-first test proving 34 timeouts + 1 `HTTP 502` verdicts `outage` (exit 0)
  while one genuinely answered query still verdicts `quiet`.
