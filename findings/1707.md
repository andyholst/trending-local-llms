## Finding

- **Evidence:** `scripts/update_trending.py::is_upstream_timeout` decides a transport failure by bare substring tokens — `"522"`, `"504"`, `"502"`, `"503"` appear in the token tuple and are matched with `token in text`. This change makes the timeout outage prong excuse any all-failed run with `timeouts > 0` as a non-blocking `outage` (exit 0). An unrelated reason string that merely CONTAINS one of those digit sequences now turns a blocking `quiet` verdict green: `RuntimeError("parsed 502 bytes from the page")` classifies as `is_upstream_timeout == True`.
- **Why:** the outage verdict is deliberately non-blocking because `live-smoke` gates `auto-merge`; a false-positive classification removes that gate for a genuine query-set regression — exactly the class issues #291/#296 exist to prevent. The blast radius grew with this change because `timeouts` is now the sole discriminator for the transport outage prong.
- **Done when:** the gateway-token half of `is_upstream_timeout` matches an HTTP status SHAPE (for example `HTTP Error 502`, `502 Bad Gateway`, `statusCode: 502`) rather than a bare digit sequence, with a RED-first guard proving that a reason containing an incidental `502` stays `quiet`/exit 1 while the measured run-45526182085 shape (`34 × read timeout + HTTP Error 502: Bad Gateway`) stays `outage`/exit 0.
