# Findings

## An unverified sweep rebase does not redden the pr-health sweep by itself

- **Signature:** pr-health-unverified-rebase-not-red
- **Evidence:** `scripts/pr_health.py::main` ends `if not silent: return 0` — the exit code reads ONLY the silent-PR verdict, and `run_rebaser`'s new `REBASED but CI UNVERIFIED: …` outcome (issue #1616) is printed but never consulted by it. Measured on this branch: driving the real script over a github-shaped fixture whose planted run carries `{"jobs": []}` prints `rebaser #7 … REBASED but CI UNVERIFIED: … ZERO jobs …` while the process still exits 0 when the PR is not otherwise silent (`tests/test_pr_health.py::test_the_sweep_rebases_but_reports_unverified_when_the_new_head_scheduled_no_jobs` records the outcome, not the code).
- **Why:** the sweep's contract is that a red round means something needs a human. A rebase that moved a branch onto a head GitHub will not schedule jobs for is exactly the state the owner has twice had to repair by hand (PR #1607/#1608, 2026-11-24); with a green exit code the only remaining signal is the silent-PR half rediscovering the same head later, one sweep round and one deadlocked auto-merge later.
- **Done when:** `main` (or the workflow step) exits non-zero naming the PR when any rebased outcome is `ci_verified is False`, with a guard in `tests/test_pr_health.py` that plants the zero-jobs run and asserts the red.

## The CI rebase step's OWN push did not schedule jobs — the proof caught it, but the mechanism did not hold

- **Signature:** auto-merge-rebase-pat-push-still-zero-job
- **Evidence:** PR #1631, 2026-11-24T17:51Z. qa-validate's `Rebase a behind-and-clean bot branch` step rebased the branch onto the fetched master and force-pushed it with `GIT_PUSH_PAT` set (the step's env log carries `GIT_PUSH_PAT: ***`): head `e0fa73af690f1f0e10d1d803bac3dec9145766e1` got run `45453080984` = `completed/action_required` with **`jobs: []`** (`gh run view --json jobs`), and `pr-closure` `45453081188` the same. The new proof in `scripts/pr_health.py::verify_rebased_ci` read exactly that and exited 1, so `auto-merge` went red instead of squashing a head nothing scheduled — the guard worked, and the mechanism it guards (#1115's PAT push) did not. A host re-push of an empty owner-identity commit minutes later (`da16319f`) produced run `45454578526` with **3 jobs**. The PR touches no `.github/workflows/**` path, so this is not the #1123 approval-hold shape.
- **Why:** the issue's premise is that pushing through the PAT-rewritten remote schedules real CI. Measured once, in the real step, it did not — so either the rewrite is not taking effect in that job (the checkout's remote URL, an `insteadOf`, or the secret resolving empty while still masking as `***`), or that PAT's pushes are treated differently from a collaborator OAuth push. Until this is known, every bot rebase in `qa-validate` still produces a held 0-job head and the new proof reds the merge job on every rebase — loud, but no merge lands without a human or a host re-push.
- **Done when:** the rebase step prints its seam output on failure (today `OUT=$(make auto-merge-rebase …)` dies under `set -euo pipefail` before `printf '%s\n' "$OUT"`, so the `push identity:` line never reaches the log) AND the pushed identity is asserted from GitHub's own run (`gh run view --json …` actor/`triggering_actor`) so a `checkout-credential` push is provably distinguished from `owner-pat`; then either the PAT path is fixed or §6s's claim is corrected with the measurement.

## The CI proof's 60 s bound is unpinned by any measurement of the real scheduler lag

- **Signature:** rebase-ci-verify-bound-unmeasured
- **Evidence:** `scripts/pr_health.py::CI_VERIFY_WAIT_SECONDS = 60`; on timeout `verify_rebased_ci` answers False `… CI scheduling is UNPROVEN`, and `scripts/auto_merge_rebase.py` turns that into exit 1. Nothing in the tree records how long GitHub actually takes from a branch push to the created `pull_request` run (the #1115 evidence names run ids and conclusions, never a push→create delta).
- **Why:** a bound that is too short reds a healthy rebase for a slow scheduler — self-healing (the push fires its own qa-validate run, whose `auto-merge` then sees a current branch), but each occurrence costs a run and a red board signal; a bound that is too long stalls every sweep round that rebases a branch. The number is a guess, and a guess pinned as a constant reads as a measurement.
- **Done when:** measure push→run-created across the landed rebases (the runs' own `createdAt` against the push time is already in the gh payload) and pin the wait from that distribution, or retry the proof once after a fresh fetch before reporting UNPROVEN.
