## The shape-aware analysis gate reds a lane whose PR predates its own per-issue file, and names no remedy

- **Signature:** findings-gate-preexisting-pr-remediless-red
- **Evidence:** this run's PR #1614 was opened at head `17d271219655b5f1f32c78c4094da4064a44991c` and qa-validate run `45418629672` failed in 26 s at the sole step `An implementation-shaped PR carries its analysis (rule 6g, issue #1454)` with `[findings] FAIL .../findings/1596.md is missing — every implementation run must analyse what it touched (write `- none` when it found nothing)`. Reproduced offline: `python3 scripts/file_findings.py --check --branch fix/bare-python-plain-make-hop-1596 --body-file <PR #1614 body>` answers rc=1 with the same line. The seam came from #1493 (`scripts/file_findings.py::analysis_path`, the per-issue resolver); the red is correct — the branch encodes #1596 AND the body opens `Implements #1596`, so `findings/1596.md` is owed on either signal. But the message names only the missing path; nothing in the gate or its §8 row says a PR opened before the file existed is fixed by ADDING the file to the EXISTING branch, and the sibling seam that makes this recur (`findings/history.md` is a tracked, append-shared file while the per-issue files are not) has no recorded follow-up.
- **Why:** rule 6g makes the analysis mandatory, so a head that cannot satisfy the resolver can never go green until someone re-reads the seam and works out the remedy — a fast 26 s red that costs a full CI round-trip and a planner dispatch to resolve. Measured on the same tree: #1559's landing PR #1561 carried `findings/1559.md` alongside `findings/history.md`, while this branch (opened one rebase behind the fetched tip `e67bbd3c`) carried the OpenSpec archive and index but no analysis file; `git merge-tree origin/master HEAD` then drifts the merged `OPENSPEC.md` count by 1, so the head also needs a rebase before it can land. A lane that hits the red without the seam knowledge re-derives both facts from scratch each time.
- **Done when:** the gate (or its §8 row) states the remedy for a PR opened before its analysis file — write `findings/<issue>.md` on the EXISTING branch, no new PR — and the branch-vs-master generated-index drift is named where the merge-tree step explains its `rebase on current master and retry`, so the two facts a head needs are read from the tree rather than re-measured.

## Every pre-#1493 implementation issue has no per-issue analysis file, and nothing backfills them

- **Signature:** findings-per-issue-backfill-gap
- **Evidence:** `git ls-tree -r origin/master --name-only` over `findings/` at `1418925c` lists six tracked files — `findings/1493.md`, `findings/1496.md`, `findings/1557.md`, `findings/1559.md`, `findings/1601.md` and `findings/history.md` — while closed implementation issues reach back to #682/#689 and the historical sections live only in `findings/history.md`. #1493 moved the write seam to `findings/<issue>.md` but landed no migration, so the analysis of every implementation run before that move exists only as a section in the shared history file, and a caller resolving an older issue (or a keeper reading `history.md` to recover a rationale) gets no per-issue path.
- **Why:** the seam promises "each run owns `findings/<issue>.md`" (the guarantee `tests/test_findings_seam.py` locks), but the promise holds only for runs after the move; the earlier record is readable solely through the append-shared history file, which is exactly the shape #1493 removed for new writes. Nothing measures or names the gap, so the historical analysis stays unfindable by issue and the seam's stated invariant is quietly half-true.
- **Done when:** a migration (or a documented, tested statement of scope) makes every implementation issue resolvable to its analysis — either by filing `findings/<issue>.md` for the pre-#1493 set or by making the history file's issue sections addressable per issue — with a guard that fails when a closed implementation issue resolves to no file.
