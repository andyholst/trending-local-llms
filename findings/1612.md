# Findings

## The rule-3c note order guard the #1586 findings file proposed would still red on #1586's own mandated order

- **Evidence:** `findings/1586.md` records the shared-line hazard and proposes "a guard reads the `Rule 3c note` line, extracts its `issue #<n>` clauses and fails unless they appear in ascending issue order with no duplicate and no gap relative to the changes that declare them". Measured on this branch (Order A, head `10c885f2`): the line is `#1209, #1232, #1258, #1395, #1589, #1586`, so an ASCENDING-issue-order guard over the raw `#<n>` sequence FAILS (`#1589` then `#1586` descend) while the reviewer-approved landing is exactly that order. Ascending *issue* order is not the invariant; the invariant is LANDING order (each clause appended after its predecessors).
- **Why:** filing that as written would red the approved tree the moment it lands, and a guard that reds a correct landing teaches readers to bypass it. #1612 already fixed the half of this that reds today (the `#1395` endswith pin); the mechanical order guard needs the landing-order definition before it is worth writing.
- **Done when:** a guard reads the note, splits it into clauses, derives each clause's landing order from the clause's own issue id AND its position in the note, and fails only on a clause that MOVED EARLIER than a predecessor or was duplicated — RED-first on the measured `#1209, #1232, #1258, #1589, #1395, #1586` (out-of-order) text and GREEN on both `#1209, #1232, #1258, #1395, #1589, #1586` and `#1209, #1232, #1258, #1589, #1586, #1395`.
