## The `--json … -q|--jq …` exemption skipped its own stated reason

- **Signature:** gh-json-jq-exemption-unenforced
- **Evidence:** measured on `origin/master` = `e93bc67dabd1dbdb1e6e257c0b2f24316fbe53e0`: `python3 scripts/gh_json_fields.py --check-argv 'gh pr list --json number -q .title'` printed `[gh-json-fields] OK` and exited 0, while `scripts/gh_json_fields.py::check_argv()` validates the `--json` list and then skips the whole projection half under `if "--json" not in argv:` — so `.title`, a field the argv never listed, was never compared. `gh` answers objects carrying only the requested fields, so `.title` yields `null` at RUN time: the exact build-time-vs-run-time class #1158/#1160 were filed for. It is LATENT, not live: the five shipped composite sites are self-consistent (`openspec_archive_check.py:108`, `issue_verdict.py:417`, `issue_queue.py:194`, `bot_health.py:183` — each `repo view --json nameWithOwner -q .nameWithOwner`; `keeper_pr.py:161` — `--jq '[.[] | select(.headRefName | startswith("fix/"))]'` inside its own `number,headRefName,…` list).
- **Why:** the exemption's comment claims "that half already validated the field this projection re-reads"; nothing checked it, so a renamed/mistyped projection field shipped a silent `null` instead of reddening `make lint`.
- **Done when:** `check_argv()` enforces the reason — when the SAME argv carries `--json <fields>` AND `-q|--jq <expr>`, every path `jq_paths(expr)` reads must name one of the listed fields (`-q|--jq` path outside the list is refused, naming the path and the list), a path `jq_paths` cannot read stays tolerated, and the five shipped shapes stay green. Landed in this PR with `tests/test_gh_json_fields.py::test_a_planted_json_projection_path_is_refused` (RED on `git show origin/master:scripts/gh_json_fields.py`, GREEN here) plus the five-site pin in `::test_the_json_projection_and_fieldless_api_calls_are_exempt`.
