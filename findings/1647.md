# Findings — issue #1647 (an unverified pr-health REBASE=1 sweep exits green)

Analysis of what this landing touched (rule 6g). Two items; neither is fixed inside
this change.

## Residual: the CI-step PAT push still yields a 0-job held run (owner credential scope)

- **Evidence:** filed by tll-reviewer as #1646 from its PR #1631 review; measured runs
  `45453080984` (head `e0fa73af`) and `45462716032`/`45462715987` (head `d168eca6`) — every
  qa-validate/pr-closure run created by the CI step's own `GIT_PUSH_PAT` rebase push arrived
  `completed/action_required` with `jobs: []`, while a host collaborator re-push produced 3 real
  jobs. This change makes that state LOUD (the sweep reds); it does not make the push schedule.
- **Why:** the credential scope behind `FIXBOT_DISPATCH_TOKEN` is an owner act (rule 6v — no lane
  may change credentials or collaborator access), so the mechanism gap is escalated rather than
  repaired here.
- **Done when:** the owner rules on the PAT identity/scope (or approves the held runs), and a
  dispatched follow-up asserts the pushed identity from GitHub's run.

## Residual: an unverified-but-pushed round is not announced on the PR thread

- **Evidence:** `scripts/pr_health.py::main` comments only `failed_rebases(...)` (issue #964: a
  rebase git REFUSED, branch left untouched). An outcome that PUSHED and then failed proof
  (`REBASED but CI UNVERIFIED`, `ci_verified is False`) now REDS the sweep but leaves no comment
  on the PR thread, so the branch's author sees a red `pr-health` run and nothing on their PR.
- **Why:** deliberately out of scope. #964's marker contract is keyed on a failed (branch, head)
  pair and names a remedy for an untouched branch; an unverified push has a different remedy
  (prove/re-push the head) and folding the two would change the registered marker's meaning.
- **Done when:** a separate small change adds a deduplicated announcement for the
  pushed-but-unverified shape, or the planner rules the red run log is enough.
