# Findings — issue #1866 (DGX Spark / GB10 token vocabulary)

## The dgx/gb10 token addition shifts six real-store rows — enumerate and decide each

- **Evidence:** Real-store probe at base `e711acd6e1d48b99150b6e0c8ac94706cdc2dc16`, driving the REAL `measurement_backend()` over `flatten_store(models.json, measurements.json, posts.json)` with the store's own `engines` registry — once with the shipped `_CUDA_HW` and once with `dgx`/`gb10` appended. Exactly six rows change classification; every other DGX-Spark/GB10 row already carried another NVIDIA token (`nvidia`/`cuda`) and is unchanged. `_CUDA_HW` is read by `is_nvidia_gpu()` (before the registry), by `is_amd_gpu()`'s "and no NVIDIA token" exclusion, by the CPU-vs-GPU check and by the keyword fallback, so a single token addition reclassifies any row whose hardware names it. The complete before/after table is below.
- **Why:** A silent reclassification would put a measurement in the wrong backend column. Each shifted row therefore gets an explicit call. All six follow the rulebook precedence (AGENTS.md rule 6: an AMD GPU/APU is ROCm only when the hardware names "no NVIDIA token") and PR #1864's documented design: explicit NVIDIA hardware wins over a single-backend engine registry (`TensorFold -> Metal`, `ExLlamaV3 (ROCm fork) -> ROCm`). No stored value is edited.
- **Done when:** all six rows below are accounted for and the real-file guard verifies each one's documented decision; `make render-readme` moves the DGX-Spark figures out of the Metal column with no unrelated churn; Apple/Mac and explicit-CPU-only precedence is unchanged; no schema, contract, data value or table-shape change lands.

Row-by-row decisions — the real-file guard parses every `- DELTA ` line and checks the row's actual classification against its recorded decision:

Per-row rationale:

1. First three — the #1866 named rows: DGX Spark / GB10 is NVIDIA hardware; the engine is registered TensorFold->Metal, so the explicit NVIDIA token must win (PR #1864's rule). Shift to CUDA is the fix the issue asks for.
2. qwen3.6-35b-a3b (two rows): the hardware names an AMD APU as PRIMARY evidence and the GB10 box in parentheses. The rulebook classifies an AMD APU as ROCm only when it names "no NVIDIA token"; GB10 is an NVIDIA token, so these rows leave ROCm. The same t/s values (87.2 / 188.9) are published by the same author on the same date under sibling rows naming "NVIDIA DGX Spark (one)" (source posts `niklaslenz_ai/status/2111621869157044461` and `.../2111204284453044383`), so NVIDIA hardware evidence is genuine. Shift to CUDA is correct.
3. minicpm-v-4.7 (ROCm fork): hardware is "DGX Spark (GB10, 128GB unified memory)" — an NVIDIA box; the ROCm-fork engine name is registry evidence only and must lose to explicit NVIDIA hardware (the planner's named example). Shift to CUDA is correct.

## Contradictory AMD-APU-plus-GB10 hardware strings need a separate data correction

- **Evidence:** `qwen3.6-35b-a3b` rows cited above carry the hardware string `Radeon 8060S / Strix Halo 128GB (ASUS Ascent GX10, GB10)` — an AMD APU and an NVIDIA GB10 box in one value — while sibling rows with identical t/s values name only `NVIDIA DGX Spark (one)`. The raw captures (`data/raw/amd-20261019-180230.json`, `data/raw/metal-20261024-195508.json`) carry the same contradictory string with no post text to disambiguate.
- **Why:** the classification precedence is settled by this change (GB10 is NVIDIA), but the underlying hardware text is internally contradictory and a reader cannot tell which box produced the figure. This is a data-quality gap in the store, not a classifier defect, and is deliberately NOT fixed here (no data value changes in this delivery).
- **Done when:** a future, separately-dispatched data change reconciles the source-post hardware text so each measurement names one box; until then this finding stays open. No `tech-debt`/`data-gap-analysis` label is applied by this lane.
