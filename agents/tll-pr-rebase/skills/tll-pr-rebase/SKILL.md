# TLL PR Rebase Conflicts

## When to use

Use this when the owner, or a comment from `tll-planner`, asks this profile to sweep the open PRs of
https://github.com/andyholst/trending-local-llms and rebase the genuinely-`CONFLICTING` ones onto the latest
`origin/master`.

## Standing fleet behavior (owner-mandated, issue #703/#704)

- **Fetch before you measure / before you branch.** `git fetch origin master` (and the branch under rebase
  via an explicit refspec) immediately before any measuring or branch cut; work from a worktree off the sha
  fetched in that moment. `origin` is the canonical remote; the branch is `master`; there is NO `upstream`
  remote — never invent one. Never branch from a sha quoted in a chat (stale by the time you read it). Write
  the fetched sha into your first comment.
- **Start new work from a worktree**, never the owner's checkout at
  `/home/asimov/repository/git/trending-local-llms`. `git worktree add -B <branch> <absolute-path> <sha>` —
  give the worktree an ABSOLUTE path or it can land inside the clone.
- **CLAIM protocol — post before you start.** Before touching a PR, comment on its bound issue:
  `BOT tll-pr-rebase · working on #<id> · branch <ref> · blocked on <x|none> · next <y>`.
- **READ-THE-THREAD first.** Before you start, read the PR/issue thread for another lane's LIVE
  working-claim on the SAME PR (a `BOT … working on` record or a `bot-claim:` marker). If another lane has
  claimed it, DO NOT touch it — report the collision to `@tll-planner` on the same thread and await
  re-dispatch. Never two writers on one PR.
- **Message the owning lane before rebasing an ongoing PR** — `@tll-implementer` (code PRs), `@tll-security`
  (findings), `@tll-reviewer` (gap fixes), `@tll-tester` (test-led PRs) — with the id, the measured head sha,
  and what you are about to do; post the conclusion on the PR after. Only proceed when they decline or the
  planner hands it over.
- **Finish with a signed record + report to the planner.** End every rebase with a comment (new head sha,
  what changed, the run id/command that proves it, anything left open) and relay the same two lines to
  `@tll-planner`.

## Procedure

1. Do not create a cron job. If `cron/jobs.json` exists, stop and tell the owner. This fleet does not run on a timer.
2. Read `SOUL.md` in this profile. The repo is https://github.com/andyholst/trending-local-llms, branch `master`, canonical remote `origin`.
3. **Survey**: `git fetch origin master`, then
   `gh pr list --repo andyholst/trending-local-llms --state open --json number,headRefName,baseRefName,isDraft,mergeable,mergeStateStatus`.
   Rebase ONLY `mergeable=="CONFLICTING"` / `mergeStateStatus=="DIRTY"` — one PR at a time. Never rebase
   `MERGEABLE`/`BEHIND` speculatively: master advancing under a mergeable PR is fine until a merge
   re-dirties it. Exclude drafts and PRs another lane is live-claiming (`BOT … working on` / `bot-claim:`).
4. **Publish the sweep before touching anything.** Post one comment per sweep on #682 (the fleet parent)
   naming `base sha · PR# · branch · head before → after`, posted before the first push. A rebase that is
   not announced is indistinguishable from a lane losing its work.
5. **Claim + read-the-thread**: post the `BOT tll-pr-rebase · working on #<id> …` record, verify no other
   lane has a live claim on that PR, message the owning lane.
6. **Worktree**: `git worktree add -B pr<N>-rebase /home/asimov/repository/git/trending-local-llms-wt/pr<N> origin/<branch-at-fetched-sha>`. Never the owner checkout.
7. **Rebase**: `git rebase refs/remotes/origin/master`. If the PR's base is `master` (read `baseRefName` per PR — a PR stacked on a feature branch must NOT be rebased onto master; report it instead).
8. **Resolve as unions of both intents.** TLL's habitual conflicts:
   - `data/models.json` + `data/measurements.json` + `data/posts.json` (split store): keep `origin/master`'s version except the branch's own additive rows; NEVER drop a measurement (a dropped key / shrunk value is the #463/#525 alarm class).
   - `README.md`: generated by `scripts/update_trending.py` — regenerate, never hand-merge; `git diff origin/master -- README.md` must be only the branch's intended change.
   - `openspec/changes/<slug>/` change dirs: keep both sides' additive changes.
   - If the two sides genuinely contradict (a real redesign), stop and report — never invent a third behaviour.
9. Keep the branch at one commit (the TLL norm); preserve author `Andy Holst <andy.holst@protonmail.com>`; never re-author.
10. **Gates before push**: run the repo's gate green on the rebased head (`validate` + `live-smoke` + closure + guard — the `qa-validate` set). A rebase that ships a red head is not a rebase.
11. **Push**: `git push --force-with-lease="refs/heads/<Br>:origin/<Br>" origin "HEAD:refs/heads/<Br>"`, lease on the ref you actually fetched. Verify `git rev-parse HEAD` == `git rev-parse origin/<Br>`.
12. **Report**: read back `gh pr view <N> --json mergeable,mergeStateStatus,headRefOid`; post the finish bookend (new head sha, what changed, the run id / gate command that proves it); relay start+finish to `@tll-planner`.

## This lane

- Rebase ONLY the genuinely-`CONFLICTING` subset, one PR at a time, onto freshly-fetched `origin/master`.
- Resolve conflicts as unions of both sides' intent; a token-level union that drops one side's change is wrong even when the suite passes.
- Do not review product scope, do not approve, do not arm auto-merge, never `gh pr merge` — the repo's gate (`qa-validate`) merges green.
- Do not push to `master`. Do not open the owner's checkout. Do not prune/remove a worktree. Do not cancel a live run. Do not print `.env` values.
- If a job fails on the branch AND on a pristine `origin/master` worktree, it is pre-existing/inherited — disclose it and the sha, do not call the rebase red. (Two known host-environment tests fail regardless: `test_openspec_archive_check` and `test_worktree_base`.)

## Pitfalls

- A SINGLE-commit branch rebased onto one-fresh master: the bottom replayed commit's parent is `origin/master`, not `HEAD^` — read `git log --format=%H <base>..HEAD | tail -1` then its `^`, never `HEAD^`.
- A stale commit-level check can show a FAILURE while a later run on the same sha SUCCEEDED — prefer the newest workflow run (`gh api …/actions/runs?head_sha=<head>`).
- A conflicting PR reports NO checks (no merge ref is built) — that is the symptom, not a broken workflow.
- Never rewrite a branch another lane is actively pushing; a rejected `--force-with-lease` means another actor moved the branch — re-fetch, check whether it is already `MERGEABLE`/resolved, report and stop; never escalate to a bare `--force`.
- A local branch named `origin/master` can shadow the remote-tracking ref — rebase with `refs/remotes/origin/master`.
- After a rebase that reports success, `git grep -lE '^(<<<<<<<|>>>>>>>)' -- .` must print nothing — conflict markers can survive `--continue` even inside a "generated" file.
- When the PR reads `CONFLICTING` but `gh api …/pulls/<n> .head.sha` lags the branch ref after a push, believe the branch ref; re-read the API, never re-rebase to "fix" a conflict that exists only on a stale PR-head ref.
- A Hermes cron or a new GitHub Actions `schedule:` is the wrong tool. The owner asks on the host; the data sync is the existing weekly refresh, not a new timer.
- `tech-debt` and `data-gap-analysis` hand the issue to the Actions implementer. This fleet uses `enhancement`.
- Do not print credentials, tokens, or `.env` values. Name the sha you measured.
