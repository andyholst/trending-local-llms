# TLL Reviewer

## When to use

Use this when the owner, or a comment from `tll-planner`, asks this profile to work on https://github.com/andyholst/trending-local-llms.

## Procedure

0. **Fetch latest before any measure/branch (owner-mandated, #703).** Run `git fetch origin master` (origin is the canonical remote, master is the branch, no upstream remote) and work off the sha fetched in that moment. A sha from chat is stale. Record the sha you measured.
1. Do not create a cron job. If `cron/jobs.json` exists, stop and tell the owner. This fleet does not run on a timer.
2. Read `SOUL.md` in this profile. The repo is https://github.com/andyholst/trending-local-llms, branch `master`.
3. **CLAIM / READ / REPORT before starting (owner-mandated, #703).** Post the `BOT tll-reviewer · working on #<id> · branch <ref|none> · blocked on <x|none> · next <y>` record on the issue. READ the issue thread first: if ANOTHER lane has a live working-claim on the same issue, do NOT start — REPORT the collision to `@tll-planner` on the same thread and await re-dispatch. Never two bots on one issue.
4. Work in a worktree created from the latest fetched `origin/master` (convention in issue #690, owner-mandated, all tll lanes). Never the owner's checkout at `/home/asimov/repository/git/trending-local-llms`; never push. Create the worktree off the sha fetched in step 0 and record that sha.
5. Do the lane work in `SOUL.md` and stop. Coordination lanes file or comment. Only `tll-implementer` writes the tree, and only after the planner names the issue.
6. Post the result on the issue. The comment is the record.

## Checks and filing

Concrete probes and the file/verify/cleanup loop live in `references/attribution-checks.md`. Reviewing an `agents/` mirror-resync (docs-only) PR — scope, per-file byte-fidelity, the post-commit-churn decision test — lives in `references/mirror-resync-review.md`. Always:

1. Flatten-loss needs TWO diffs, not one. (a) Self-consistency: render the head store into a temp copy and `diff` against the head's own committed `README.md` — byte-identical proves only that the store reproduces its own README. (b) Value-for-value: `diff` the HEAD-rendered README against the BASE (pre-split) committed README. Any engagement/trend/buzz figure that changes while `posts.json` and the measurement rows are byte-identical base↔head is a flatten-loss defect (the switch re-resolved engagement) — file it. A monotonic 'no-shrink' guard printing green does NOT prove equivalence; see `references/attribution-checks.md`.
2. Run the within-model AND cross-model duplicate probe from the reference over `data/models.json`.
3. Trace a suspicious row's `source_post` back through `data/raw/*.json` and confirm the model that carries the row is in the set the post actually measured (the `why`/`quant` text names the models and their t/s).
4. Dedup BEFORE filing: `gh issue list --state all --limit 40 | grep -i '<model or class>'` and `gh issue list --label enhancement --search '<model>'`. If an open finding already covers the SAME mechanism (a tester or another lane may have filed it), do NOT duplicate — confirm it independently in your verdict comment and cite the existing issue number. A near-miss in a different mechanism is filed as a NEW issue only if you state the distinction in the body so the planner does not merge it (e.g. "a row whose own text names a different model" vs "one model's number copied onto a model the post never measured").
5. Write the draft body to a file and run `make issue-message-check BODY_FILE=<draft>` BEFORE you file (issue #1730). A non-zero verdict blocks the filing — repair the draft and re-run; do not hand-edit a body after it landed. Only when the verdict is zero, file with `gh issue create --repo andyholst/trending-local-llms --label enhancement --body-file <draft> ...`, then verify with `gh issue view <n> --json number,title,labels,state` — confirm the label landed on `enhancement`.
6. Remove your worktree when done: `git worktree remove <path> --force`, run FROM INSIDE the repo that owns the worktree — when your clone is a bare repo (`repo.git`) with worktrees as siblings (`head/`, `base/`), `cd repo.git && git worktree remove ../head --force`. Running it from the parent dir gives `fatal: not a git repository`. Never prune another lane's worktree.
7. When `tll-planner` names a fix / re-pushed PR head to verify, review at that EXACT sha — the recipe (data-identical rule, guard-is-real-logic check, README render diff, pre-existing-vs-new drift, corrected-claim check, CI gate) is `references/attribution-checks.md` §5. Report CI check states at the head and defer the test verdict to `@tll-tester`; never treat a local green as merge readiness.
8. If the named head is `MERGEABLE:CONFLICTING` or is still based on a pre-split/old-layout base, do NOT review that stale head — the base shifts under the rebase and a verdict on old-base data is void. Post a signed record on the PR stating the conflict, confirming the tracked issue is genuinely still un-fixed on current `origin/master` (grep the code for the mechanism it names), and listing exactly what you WILL verify on the rebased head (attribution gone, value-fidelity holds on the split store, delivery shape, gates at the new head). Then hold until the rebased head lands.
8b. A PR that closes an issue whose OpenSpec change is still ACTIVE reds `validate` on "OpenSpec lifecycle" — reproduce it offline in ~3 s before reporting CI shape: `python3 scripts/openspec_archive_check.py --pr <n>` (reads only the tree + the PR number). Remedy is `make openspec-record-pr ISSUE=<id> PR=<n>` (records AND archives) or `make openspec-archive NAME=<slug>` + `make openspec-index`. A `PR:` line in the index is NOT enough (#866).
9. When the planner asks you to assess an issue that carries `tech-debt` / `data-gap-analysis` (the Actions implementer's queue, NOT this lane's filing lane), do NOT re-file, add a label, or touch it — verify its actual state on the named master sha (grep the code for the mechanism/guard the issue names) and post a REPORT-ONLY status record citing the sha. Confirm still-open/closed honestly against the code; that is the full extent of this lane's duty on another lane's labeled issue.

10. **Before any PR handover, run the live body preflight (issue #1716).** Run `make pr-message-check PR=<n>` on the PR you are about to hand over or review. A non-zero verdict means DO NOT post the `pr #<id>` / `reviewing #<id>` handover comment — repair the body and re-run until the verdict is zero.

## Pitfalls

- A near-duplicate you did not search for is a wasted issue. Grep open and closed issues for the model id and the class before filing.
- A within-model-0 result is not a clean bill of health; run the cross-model probe too. The architect's claim usually holds only within-model.
- A Hermes cron or a new GitHub Actions `schedule:` is the wrong tool. The owner asks on the host. The data sync is the existing weekly refresh, not a new timer.
- `tech-debt` and `data-gap-analysis` hand the issue to the Actions implementer. This fleet uses `enhancement`.
- Byte-identical self-render (the head store reproduces the head's committed README) is NOT a clean flatten-loss bill of health. The switch can select a different engagement source, so head renders its own README perfectly while every buzz figure differs from the pre-split README. Diff HEAD-render against BASE-committed, and never trust a guard that only fails on counter shrink / dropped identity — upward drift (counter grows) is invisible to it.
- A duplicate tuple or engagement drift you find in a fix PR may be PRE-EXISTING, not introduced by the fix. Compute the same probe at BASE; if the set is identical to head, report it as "pre-existing, unchanged" — do not pin it on the PR under review. Many apparent `(model, engine, source_post)` duplicate keys are legitimately distinct measurement rows (different quant/date/tps on one post), not attribution collisions.
- A 'corrected claim' fix can be PARTIAL: the same false sentence often lives in several sibling docs of one change dir (proposal.md, spec.md, tasks.md). `openspec-check` validates only that task boxes are ticked, not their wording, so a fix that cleans the proposal leaves tasks.md stale, the issue auto-closes COMPLETED, and the falsehood ships beside the correction. Grep the claim term across the WHOLE head openspec tree and classify each hit (in-scope residual → blocker; honest disclosure → good; unrelated dir → out of scope) before declaring a corrected-claim fix clean. See `references/attribution-checks.md` §5f.
- Verify authorship and diff scope with FULL SHAs. A bare short sha in a worktree that does not share base's refs raises 'unknown revision or path not in the working tree' — this is a ref-visibility artifact of the worktree, not a real missing commit; re-run with the full 40-char shas. Likewise a fresh `git clone --bare` already carries origin's refs — cut the worktree directly with `git worktree add <path> <full-sha>`; `git fetch origin origin/master` in that bare clone errors `couldn't find remote ref` because the remote's ref is `master`, not `origin/master`.
- **Never measure through `FETCH_HEAD` in this shared checkout.** Every lane fetches into the SAME clone, so a concurrent `git fetch origin <other-branch>` overwrites `.git/FETCH_HEAD` between two of your commands and `git diff <base>...FETCH_HEAD` resolves to whatever was fetched LAST — you silently review a revision nobody named. Pin the explicit full sha or the `origin/<branch>` remote-tracking ref in every read (`git diff <base> <head-sha>`, `git show <sha>:<path>`), and echo `git rev-parse <sha>` immediately before measuring so the bound sha is in the transcript.
- **A red `validate` at the "OpenSpec index on the merge tree" step is a STALE-BASE verdict, not a code defect.** When `master` advances while a PR sits open, both sides edit `OPENSPEC.md` (the active-count line and the row block) and the step dies `MERGE CONFLICT ... rebase on current master and retry`; every later step (unit tests, architecture, ledger) is SKIPPED, so the head's own logic is UNVERIFIED. Reproduce offline in seconds: cut a scratch worktree at the PR head, `git merge --no-commit --no-ff origin/master`, `git status --porcelain` — only the genuinely conflicting files show (often just `OPENSPEC.md`). Report HOLD naming the conflicting paths and the remedy (rebase onto the fetched master sha + `make openspec-index`), and check whether the PR's headline change is ALREADY UPSTREAM: `git show origin/master:<file> | grep -c <symbol>` — if master landed the same edit while the PR sat, the delta shrinks to the PR's tests/guard, and the verdict must say which part still carries unique value.
- **Prove a NEW gate with BOTH polarities, not a head-only green.** A guard that parses a text artifact (Makefile, contract, store, README) is not evidenced by passing on head alone: it can be vacuous (empty scan set, wrong prerequisite closure, predicate that matches nothing) or wrong-signed. Import or replicate its PURE parse helpers in a throwaway script and feed them the BASE and the HEAD text: require RED on base (naming the exact offending recipe/row/key) AND GREEN on head, and quote both strings as evidence. A guard that cannot name its base offender proves nothing even when head is green.
- "Differs from current host" is NOT "bad copy." Host profiles are live and keep changing while a mirror-resync PR sits open. Before pinning a content mismatch in an `agents/` copy as a defect, compare the commit author time (`git log -1 --format='%ci' <head>`) against the host file mtime (`stat -c '%y' <host-path>`): host mtime AFTER commit time is post-commit host churn (mirror was faithful at author time — report as noted residual, non-blocking, recommend the owning lane re-sync that one file). Without this test every resync review becomes a false blocker. See `references/mirror-resync-review.md`.
- Lane counts and inventory in a dispatch are prose; the `git ls-tree <sha>:agents/` count is fact. Reconcile the two yourself and report the real numbers rather than repeating the dispatch's enumeration back to it.
- A mismatch from a batch compare loop is a hypothesis, not a finding — confirm it with a direct, correctly-pathed `cmp` of the exact two files. A loop that read the wrong sub-path (e.g. a lane file vs its `skills/<lane>/SKILL.md`) reports phantom mismatches on files that actually match.
- A stray deliverable artifact committed at the tree ROOT is delivery-shape churn, not a data defect. A `.pr<NNN>.md` (the implementer's PR-body/deliver draft) or any file outside the change dir / code / tests is a dead file: `git diff --name-only <base> <head>` it, then `grep -rn '<name>' . --include='*.py' --include='*.md' --include='Makefile'` — referenced nowhere and part of no gate confirms it. Report it as a non-blocking note under the #690 lens (recommend the implementer strip it in an amend or tiny follow-up), NOT a blocker on the logic under review. Distinguish it from real scope creep in code/data.
- When the planner re-pushes a corrected head (e.g. the stray artifact stripped) and asks you to confirm, fetch the OLD head sha directly and diff old→new — a force-push-with-lease leaves the old object fetchable by sha until GC even though a fresh clone lacks it. Exactly one `D <stripped-file>` and nothing else proves your prior PASS on the logic TRANSFERS unchanged; then just re-check CI at the new sha and post a distinct re-confirm comment (do not rewrite the original verdict). Recipe: `references/attribution-checks.md` §5b3.
- A fix PR that touches only tests/OpenSpec/docs has data files byte-identical base↔head; prove it (`diff -q base/data/X head/data/X` per data file) and say so — that single fact rules out data/attribution regression and scopes the review to the guard, the README, and the docs claims.
- A local green on a hand-rolled test module does NOT prove every test ran. `tests/test_*.py` here use a `def main()` that CALLS each `test_*`; a `test_*` that is defined but never called from `main()` is dead — the module still prints `N passed` while CI's `test_workflows.py` hygiene rule ("every `test_*` is called from main()") reds. Before declaring test hygiene clean, list every `def test_` and confirm each has a matching call inside `main()`; grep `def main` NOT `def main():` — the runner may be annotated `def main() -> int:` and a `def main():` literal grep returns a false negative. This is why a local pass is not merge readiness even when the module is green. A module that prints `SKIP: <reason>` and exits 0 is NOT a pass either — treat a declared skip (a missing host-only test dep is the common one) as CI-owned and UNVERIFIED, and say so in the verdict; never count a skipped module toward local evidence or quote its exit code as support. Also check the OTHER direction: a `test_*` listed TWICE in `main()` runs its assertions twice and inflates the printed count — diff the module's line count against the lane's claimed count, and `grep -c '<distinctive assertion label>'` to prove single execution.
- `validate.load_store` does not exist — the loader lives in `update_trending` (`import update_trending as ut; ut.load_store()`); `validate` only calls it. A guard probe that does `validate.load_store()` dies with `AttributeError`.
- Product-visible order is the CATALOG `models` array in `models.json`, NOT the dict key order of `measurements.json`. `flatten_store` iterates the catalog and pulls rows by model id, so a removed-then-reinserted model's key relocating to the END of `measurements.json` is render-invisible churn — do NOT flag it if the catalog `models` id list is preserved in place (compare that list base↔head). A real order regression only shows when the `models` array itself is reordered.
- The persistent terminal shell's CWD can point at a scratch dir deleted underneath it, so a later `cd <relative>` or bare command fails with `getcwd: cannot access parent directories`. Pass an absolute `workdir` on the terminal call instead of relying on the sticky CWD, and never `cd` into a dir you just deleted.
- **A prerequisite that PRINTS poisons any consumer that captures the target's stdout.** Routing an artifact target (a `make <t> … > file`, `TITLE=$(make <t> …)`, or `subprocess.run(..., capture_output=True)` in a keeper script) through a prerequisite whose recipe is not `@`-silenced — or whose script prints to fd 1 — prepends make's echoed recipe line plus the script's own output to the artifact. Measured on PR #1451: `pr-body`/`pr-title`/`architecture-pr-body` gained `python-env-image`, so `issue-bot.yml` `make pr-body … > pr-body.md` and `TITLE=$(make pr-title …)` captured `python3 scripts/ensure_image.py ensure-python` + `python-env: … present locally`. Check BOTH branches of any `IN_CONTAINER`/`/.dockerenv` fork: the suite runs in-container (escape silent), so only a forced-host probe (`IN_CONTAINER=` + a stub `docker` on PATH) reveals the leak; and `test_a_recipe_redirected_into_a_file_never_echoes_its_own_command` reads a target's OWN recipes, never its prerequisites.
- **A "union" PR needs an OBJECTIVE duplicate probe, not a diff read.** For a host-ahead skill-mirror union (the #1462/#1463 class), `git diff <base>...<head>` interleaves insertions and hides near-duplicates. Prove BOTH properties with counters over the BLOBS: (a) losslessness — every non-trivial base line's multiset count must be `<=` head's (`git show <base>:<path>` vs `git show <head-full-sha>:<path>`, never `FETCH_HEAD`); (b) no NEW duplicates — any phrase whose count GROWS base→head is merge debris UNLESS the host copy also carries it. Always compare the HOST copy too (`~/.hermes/profiles/<lane>/skills/<lane>/SKILL.md`): host=1 and head=2 means the merge INVENTED the second copy. Measured on #1463 head `b2a26036`: five planner phrases plus a dangling `chasing it.` fragment went 1→2 while the host stayed at 1 — and the pinned test still exited 0.
- **A data-only KEEPER whose claimed change is ALREADY UPSTREAM: attribute it by scanning the DATA FILE's history, not the PR diff.** A rebased keeper's net `git diff <merge-base> <head>` can contain NONE of what its title/body claims, because master landed the same edit from a sibling keeper first (measured PR #1470: title `normalize ledger targets to bare make targets`, but its diff vs base carried only 4 appended rows + 2 annotations + a guard test — the 15 bracketed `targets` spellings were stripped earlier on master by `73926b90`). Walk every commit that touched the file (`for c in $(git log --format=%H --since=<win> -- <data-file>)`) and probe each blob for the offending shape to NAME the commit that actually changed it; then say which part of the PR still carries unique value. Never report the claimed change as missing on the strength of the net diff alone.
- **A red-proof of a data guard needs the PRE-change BLOB planted, not just a base-checkout run.** Swap `git show <pre-change-sha>:<data-file>` into the worktree's tracked path, run the module's own `main()`, quote its exit code and FAIL line, then `git checkout -- <path>`; a base-checkout run proves nothing when master already fixed the shape (the guard would pass there too).
- **Run the real pin module at the head in a throwaway DETACHED worktree; a green pin is not the property.** `git worktree add --detach <scratch>/wt <head-full-sha>`, then `python3 tests/<module>.py` — these modules carry their own `def main() -> int`. Prefer the module's own `main()` over `python3 -m pytest`: plain pytest reports the whole module as ONE test and the module's `check()` FAIL lines stay invisible unless the `[check-parity]` wrapper happens to print them (a host that ships pytest 8.x gives a green-looking `-q` run while `_checks_failed=1`). Quote the module's exit code NEXT TO the duplication you measured: a needle-presence pin passes while the union is broken, and that contrast is the finding.
- **A green PR can AUTO-MERGE while you review.** Re-check `gh pr view <n> --json state,mergedAt,mergeCommit` and `origin/master` BEFORE posting the verdict: if it merged, a HOLD can no longer block anything — re-frame it as a shipped defect (verify the defect is on master), verify close-hygiene on the linked issue, and hand the repair to `tll-planner` as a follow-up issue rather than a branch repair.
- The checkout at `/home/asimov/repository/git/trending-local-llms` is the owner's. Do not edit it.
- **A read-only REVIEW dispatch may forbid a worktree — review the remote branch in place.** `git fetch origin <branch>` is read-only (it creates no branch); read through the remote-tracking ref with FULL shas: `git show refs/remotes/origin/<branch>:<path>`, `git diff origin/master..refs/remotes/origin/<branch> -- <paths>`. To RUN the head's own tests without checking anything out, extract a throwaway tree with `git archive <head-full-sha> | tar -x -C <scratch>` (or `git init <scratch>; git remote add origin <owner-repo>; git fetch origin <head-sha> master; git checkout -B head <head-sha>` when you also need to reproduce a merge) and run the module's OWN `python3 tests/<mod>.py` there — never create a registered worktree or a branch in the shared clone. Reproduce a GitHub "OpenSpec index on the merge tree" red with BOTH `git merge-tree --write-tree origin/master <head>` and a real `git merge --no-commit --no-ff origin/master`; require them to agree before calling the red transient.
- **Docker DROPS an `-e VAR` whose host variable is UNSET** — `docker run --rm -e PROBE alpine:3.20 sh -c 'env | grep -c PROBE'` answers `0` — so forwarding an optional env NAME unconditionally does NOT clobber a consumer's `os.environ.get(name, default)` fallback; only an explicit `-e VAR=` (empty value) does. Probe it live before flagging an env-forwarding Makefile change.
- **Rule-3c DESIGN review runs in SCRATCH text trees, never a worktree.** The reviewer signs off proposed `AGENTS.md`/rulebook text with NO tree write: `git show <base>:AGENTS.md > $SCRATCH/<case>/AGENTS.md`, drop the proposed module at `$SCRATCH/<case>/tests/test_<name>.py` (its own `ROOT = Path(__file__).resolve().parent.parent` then resolves), and run it for `base`, `green` (base + ONLY the proposed edits, inserted programmatically), `delete-row`, `reword-prose-but-keep-the-name`, and `drop-one-needle`. RED at base + GREEN on the exact proposed text + deletion-reds + rewording-passes is the evidence — quote exit codes, never just "the guard is names-only". For DISJOINT anchors across sibling issues (the #1482/#1586/#1589 class), rebuild ONE document with EVERY issue's APPROVED text applied in sequence and assert each needle occurs EXACTLY ONCE, then rule no-overlap/no-duplicate/no-contradiction. Name any SHARED LINE two issues both edit: a `Rule 3c note`-style append point is an ORDERING dependency, not a conflict — the later implementer re-reads the landed head and appends AFTER the earlier clause, never at a stale line number.
- **A comment-body string quoted through `gh api` is JSON-ESCAPED; decode before comparing or your diff is noise.** A design comment fetched with `gh api .../issues/<n>/comments --paginate` returns bodies where `\n` and `"` are literal backslash escapes INSIDE fenced blocks, so `text.replace("\\n","\n")` alone leaves a broken `print("` line and every byte-compare mismatches. Use `json.loads('"' + raw_fenced_block + '"')` on the extracted block, or fetch the comment body through a `json` field rather than shelling the escaped payload. Then assert BYTE-IDENTICAL between YOUR verdict's fenced blocks and the design's, and re-run the approved functions FROM YOUR OWN POSTED VERDICT (not from the design) so the sign-off is proven against the text an implementer will copy.
- **A pin module's scratch tree needs the module's OWN prerequisites, not just `AGENTS.md`.** A rulebook-pin test resolves `ROOT = Path(__file__).resolve().parent.parent` and imports the real guard (`scripts/dispatch_guard.py`) plus reads the real `Makefile` (recipe-forwarding checks) — a bare `$SCRATCH/<case>/AGENTS.md` dies `ModuleNotFoundError` or reds on unrelated Makefile assertions. Copy `scripts/` and `Makefile` into the case dir (a full `shutil.copytree` of the worktree is simplest), patch the module's copy in place, and read ONLY the summary line plus the FAIL lines. Quote the ISOLATED count for the proposed functions separately from the in-module total (e.g. 0/9 isolated vs 111/0 in-module) so a reader can tell the nine new checks from the pre-existing 102.
- **Check a rulebook row's ADDITIVITY by counting, not by reading.** Assert §7b bold-led bullet count, §8 `| \`tests/…` row count, and the `Rule 3c note` clause count all go UP by exactly one with ZERO removed lines, and that the file still ends with a newline. That is the mechanical proof the landing is non-breaking; a prose read cannot show it.
- **Docs+pin rulebook landings STILL owe an OpenSpec change, and a claimed-green `openspec-archive-check` can be false.** The `#1109` prong refuses a closing PR whose closed issues are named by no change (`closing − referenced_issues(active + archived)`), and `referenced_issues` is read from the LOCAL tree (`--root`, default the checkout where the script runs) — so a §7b/§8 docs+pin landing (the #1602/#1586 class) needs its OWN `openspec/changes/<slug>-<id>/` bound to `Issue: <id>` AND ARCHIVED on the branch, even when the guard's behaviour changes are already archived under other issue numbers. An implementer's "`make openspec-archive-check PR=<n>` rc=0" is a CLAIM, not evidence: re-run `python3 scripts/openspec_archive_check.py --repo <owner/name> --pr <n>` yourself on the tree and quote the exit code + the exact `CLOSE of #<n> — NO OpenSpec change…` line (measured on PR #1600: exit 1 while its PR body asserted "OpenSpec owes no change").

- **A design's quoted "replace this line" block drifts by a word; rebuild it from the BASE before approving.** A rulebook-row DESIGN quotes its replacement in a fence and states a char count — the count can be off by exactly the drift. Rebuild it yourself as `base_line.replace(<unique fragment>, <fragment + inserted clause>)`, prove the round-trip (deleting the insertion reproduces the base line byte-for-byte), then diff your build against the fence. Measured on #1363: the fence read `24 with none` where master read `24 had none` — 1930 chars against the claimed 1929 — a silent re-wording of PRE-EXISTING prose inside a names-only extension. Approve YOUR rebuilt bytes, quote them in the verdict, and name the delta so the implementer copies the verdict rather than the fence.
