# A stale index names the drift it actually found

**Issue:** none — found while unblocking the dispatch-bot verification pass.
**Capability:** `openspec-index` (the generated `OPENSPEC.md` and its guard).

## Why

`make openspec-index-check` is a correct gate: it fails when the committed
`OPENSPEC.md` differs from what `--write` would produce, and `make openspec-check`
runs it in CI. Its **message**, though, named the wrong cause.

Measured on `master`, while a stale index was reddening `validate` on every PR
(run 38865506979, 2026-10-16T07:15Z):

```
[openspec-index] FAIL OPENSPEC.md is stale or missing (31 active, 0 archived on disk) — run `make openspec-index`
[openspec-index]   rows exist but their data changed (issue/PR/specs/tasks)
```

`OPENSPEC.md` said `Active changes: **30**` while `openspec/changes/` held 31.
Every row was present and identical — the ONLY drift was the count line — yet the
message pointed a reader at the rows and at three fields (`issue/PR/specs/tasks`)
that had not moved. The check was right and the diagnosis was wrong, which is the
same defect class as a red live check that blames the mirror (issues #292/#293):
it sends the reader to the wrong place, and a reader who checks the rows finds
nothing wrong and stops believing the gate.

The script had exactly one catch-all branch for "rows all present, bytes differ":

```python
if not missing and not extra:
    print("[openspec-index]   rows exist but their data changed (issue/PR/specs/tasks)", ...)
```

## What Changes

- **`scripts/openspec_index.py`** — `_why_stale()` replaces the catch-all. It
  compares the committed file with the rendered one and names what actually
  differs: changes on disk with no row, rows for changes that no longer exist,
  **the count line** (quoting the number the disk needs), and **the rows whose
  data changed** (naming them). When rows and count agree but the bytes still
  differ, it says the file differs outside the rows and the count line and points
  at regeneration — instead of asserting a cause it did not find.
- **`tests/test_openspec_index.py`** — `test_a_stale_count_line_is_named_and_not_blamed_on_the_rows`
  (a committed index whose only drift is the count line must name the count line
  and must NOT claim the rows changed) and `test_a_row_whose_data_moved_is_named`
  (the other direction), both registered in `main()`.
- **`AGENTS.md`** §8 — the `test_openspec_index.py` row gains the misnamed-cause
  case. (Protected file — review-required, rule 3c.)

## Not covered

- **The merge race that produced the stale index** — the index is generated
  against a PR's base and squash-merge replaces the tree, so a PR merged out of
  order lands a count generated before its neighbours; verifying the index against
  the **merge result** is its own work item and is filed as a finding (`findings.md`),
  never fixed here (rule 6g). Master's own count has since been regenerated by a
  separate merge, so this change does not touch `OPENSPEC.md`'s numbers beyond
  listing the change directory it adds.
- **The dispatch bots.** This unblocks their verification pass; it is not part of it.
