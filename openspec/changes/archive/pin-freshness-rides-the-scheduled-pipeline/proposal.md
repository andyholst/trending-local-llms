# Hermes pin freshness rides the ONE scheduled pipeline

Issue: #1093
PR: #1150

## Why

`make hermes-pin-freshness` (issue #1091, rule 6k) compares the Makefile's `HERMES_VERSION ?=`
and the Dockerfile's `ARG HERMES_VERSION` (the #218 pair) with the upstream Hermes release
channel, files ONE marker-deduplicated `tech-debt` issue when the channel is newer, and goes red.
It was wired as a step of the `queued-alarm.yml` sweep — and `queued-alarm.yml` became
**dispatch-only** when issue #1029 (owner directive 2026-11-15, rule 6t) removed its `on.schedule`.
A dispatch-only pipeline has no cadence GitHub owes it: measured 2026-11-19, `queued-alarm.yml`
carries `workflow_dispatch` and no `schedule`, so a Hermes release newer than the pin produced
**no signal at all** until a human dispatched the sweep. The freshness check had a cadence in
prose and none in the tree — the exact failure mode rule 6l exists to prevent (a quietly aging
state must become loud on a cadence that actually arrives). `refresh-bot.yml` is the repository's
ONLY scheduled pipeline (rule 6t; `tests/test_workflows.py::test_only_the_refresh_pipeline_carries_a_schedule`
refuses any other cron), and its Wednesday slots are the cadence that does arrive.

**Owner ruling (issue #1093, 2026-11-19):** move the check to `refresh-bot.yml` — the only
scheduled pipeline — so drift alarms weekly. The dispatched sweep no longer owns it.

## What Changes

- `.github/workflows/refresh-bot.yml` — a new `pin-freshness` job: `needs: guard` (rule 6j),
  `permissions: contents: read` + `issues: write` (a job-level block REPLACES the workflow's, so
  the job files the drift issue and touches no secret and no owner PAT), the default
  `github.token`, and ONE step `make hermes-pin-freshness REPO="${{ github.repository }}"`
  (Makefile-only, rule 6m).
- `.github/workflows/queued-alarm.yml` — the step is REMOVED from the `alarm` job; the slot keeps
  a comment naming the ruling and pointing at the new home (rule 3b: prose never silently forgets
  where a step went).
- `tests/test_hermes_pin_freshness.py` — the wiring guard rewritten through ONE seam
  (`_pin_problems`): it proves the job exists in `refresh-bot.yml`, is gated by `guard`, files with
  the default token, names exactly one step, that no workflow reaches
  `scripts/hermes_pin_freshness.py` past the Makefile, AND that the dispatch-only sweep has NOT
  re-adopted the step. Planted reds: makeless step, dropped job, ungated job, unfileable job,
  cadence creeping back into `queued-alarm.yml`.
- `ARCHITECTURE.md` — §6a's `hermes-pin-freshness` row, the `queued-alarm` alarm-job prose and the
  `refresh-bot` job inventory carry the new home and the ruling; the generated inventory block is
  regenerated by `make architecture-refresh` (rule 6h).

## Impact

- **Capability:** `fleet-cadence` (which pipeline owes a cadence-bound check).
- **Pipelines:** `refresh-bot.yml` (+1 job), `queued-alarm.yml` (−1 step). No Makefile, script,
  data or contract change; `make hermes-pin-freshness` keeps its one recipe.
- **AGENTS.md:** no rule text changes — no rule named `hermes-pin-freshness` or its host pipeline,
  so rule 3c is not triggered (verified: `grep hermes-pin-freshness AGENTS.md` is empty on the base).
- **Tests:** `tests/test_hermes_pin_freshness.py` (the guard), plus the suite's existing
  cadence/guard pins (`test_workflows.py`, `test_architecture.py`, `check-workflow-guards`) which
  must stay green with the new job.

## Not covered

- Does not change what the check decides (pin/channel comparison, filing, exit codes) — issue
  #1091's spec keeps that contract untouched.
- Does not give any other pipeline a schedule (rule 6t refuses that) and does not re-schedule
  `queued-alarm.yml`.
- Does not bump either pin; a real drift is what the check exists to file.
