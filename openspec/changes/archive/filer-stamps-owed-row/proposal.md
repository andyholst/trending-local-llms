# Filers stamp the owed rulebook row at issue creation

**Issue:** [#765](https://github.com/andyholst/trending-local-llms/issues/765)
PR: #915
**Capability:** `owed-row-ledger`

## Why

Rule 6g files findings and rule 3c makes the `AGENTS.md` half of a behaviour
change review-required, so a finding that owes the rulebook a row is supposed to
declare it. `scripts/bot_markers.py` renders/parses the `owed-row` marker and
`scripts/owed_rows_check.py` reads the ledger — but NOTHING stamps a marker at
FILING time unless a `findings.md` happened to carry an explicit
`- **Owed-row:**` field. Measured on the live queue: 23 open `data-gap-analysis`
/ `tech-debt` issues, and `make owed-rows-check` answered `NO MARKER` for every
one of them — the ledger exists, the marker grammar exists, and the filers write
their owed rows as prose no machine can read. Every future owed row therefore
decays into a human re-reading threads, exactly the state issue #523 was created
to end.

## What Changes

- **`scripts/owed_row_derive.py` (new)** — the ONE derivation (rule 6d) both
  filers import. Given a Done-when/body text and the live `AGENTS.md`, it
  answers which owed-row declarations the text states:
  - a section only via `§<id>`, `AGENTS.md section <id>` or `rule <id>`, AND
    only when the id exists as a `## <id>.` heading — validated through
    `owed_rows_check.sections()`, the ledger's own heading parser, so a filer
    can never stamp a marker the ledger would refuse as `NO SUCH SECTION`
    (exit 2);
  - a needle only via a guard-row identifier the text itself names
    (`make <target>`, `tests/test_*.py`, `scripts/*.py`, a `check_*` name). A
    free quoted phrase is never derived — a phantom needle would file a false
    ledger row;
  - nothing stated → `[]` → the issue reads `NO MARKER`, which is honest.
- **`scripts/file_findings.py`** — when a finding carries no explicit
  `- **Owed-row:**` field, its Done-when goes through the derivation, and any
  derived row renders through `bot_markers.owed_row_marker` (the ONE writer)
  into the filed issue body.
- **`scripts/data_gap_analysis.py::issue_body()`** — the composed gap-issue body
  runs through the same derivation and gains a `## Owed rulebook rows` section
  carrying the stamped markers.
- **`tests/test_filer_owed_rows.py` (new)** — locks the derivation bounds and
  drives both REAL filers (`gh` stubbed on PATH) plus the REAL ledger reading a
  filed marker end to end against the REAL `AGENTS.md`.

Not covered: back-stamping markers onto the 23 existing issues (a content
decision per issue — the ledger keeps reporting them `NO MARKER` until each fix
change stamps its own), and any change to the marker grammar or the ledger
report itself.

## Impact

- `scripts/owed_row_derive.py` (new), `scripts/file_findings.py`,
  `scripts/data_gap_analysis.py` (both import the derivation — rule 6d, no
  second copy), `tests/test_filer_owed_rows.py` (new).
- `AGENTS.md` §8 gains the guard row for the new suite (rule 3c — the row this
  issue itself owes), `ARCHITECTURE.md` §6 gains the script role and §10 is
  regenerated by `make architecture-refresh`.
- Every future finding filed by `make file-findings` or `make data-gap-issue`
  whose text declares its owed row lands in the ledger automatically;
  `make owed-rows-check` can then report it `OUTSTANDING` → `LANDED` across
  changes without a human re-reading the thread.
